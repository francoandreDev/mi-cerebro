# Roadmap — items 19-21 (rutas legibles, descarga mp3, responsive mobile)

Parte de la especificación de `mi-cerebro`. Ver [`index.md`](./index.md) para el mapa completo y las reglas transversales (§4, en [`reglas.md`](./reglas.md)).

---

    - **18f. Códigos de error, docs, cierre.** _Cerrado._ Tres códigos nuevos en el área `FS_`: `MCB-FS-005` (falla de operación de `TauriNativeFs` que no es revocación de permiso — capability no cubre el path, IO nativo rechazado, disco lleno), `MCB-FS-006` (mismo caso para `CapacitorNativeFs`), `MCB-FS-007` (un adapter nativo recibió un `NativeDirRef` de browser — guard defensivo de `assertPathRef`, estructuralmente inalcanzable mientras `provideNativeFs()` siga resolviendo el adapter correcto por plataforma). `classifyFsError` (`native-fs-errors.ts`) suma un tercer parámetro `fallback: ErrorCode = FS_001` para que cada adapter elija su propio código de falla-de-IO-genérica (browser sigue en FS-001, Tauri pasa FS-005, Capacitor pasa FS-006) sin duplicar la lógica de detección de `NotAllowedError`/`SecurityError` → FS-004, que sigue siendo compartida. Los guards `assertPathRef` de ambos adapters nativos lanzan `MCB-FS-007` directo (no vía `classifyFsError`, porque no son una falla de IO sino la ruptura del invariante de DI/detección de plataforma). Agregado a `error.codes.ts` (`ERROR_CODES` + `ERROR_CODE_META`), `core/i18n/locales/es.ts`, y `docs/errors.md` (mismo template que las entradas `FS_00X` existentes). Verificado: `bun run typecheck`/lint limpios.

19. **Descarga de MP3 desde YouTube.** Sección dedicada en `/music` (o expandir biblioteca con un input de URL) donde el usuario pega un link de video y el archivo entra directo a la biblioteca, auto-organizado (título del video → `originalName`, sin pasar por el picker de archivos). Depende del paso 18: necesita `yt-dlp` embebido como sidecar de Tauri, llamado vía bridge desde un nuevo `YoutubeDownloadService` que devuelve un `Blob` y lo pasa a `MusicLibraryService.addTracks`. **Decisiones de alcance:** (1) `yt-dlp` se embebe como sidecar (`bundle.externalBin`) — el usuario no instala nada aparte, coherente con "cero fricción de configuración"; los binarios por plataforma no se commitean al repo (pesan ~15-20MB c/u), se traen con un script antes de `tauri build`/`tauri dev`. (2) **Capacitor** se deshabilitó con tooltip junto con navegador al cerrar este paso — mismo criterio que 18c con el picker (alcance consciente, no deuda) —, pero se revierte en el addendum 2026-07-18 del sub-paso 19b: `youtubedl-android` resultó ser una opción nativa madura y mantenida (Maven Central, actividad reciente), así que Capacitor gana su propio camino de descarga sin depender de un sidecar Tauri; sólo navegador queda deshabilitado. **Partido en sub-pasos independientes**, cada uno cierra por sí solo. _Cerrado._
    - **19a. Sidecar `yt-dlp` en Tauri: plugin shell + capabilities + fetch script.** _Cerrado._ `@tauri-apps/plugin-shell` (JS) + `tauri-plugin-shell` (crate, registrado en `lib.rs`) suman la capacidad de invocar binarios sidecar. `tauri.conf.json` declara `bundle.externalBin: ["binaries/yt-dlp"]`; `capabilities/default.json` agrega `shell:allow-execute` con scope `{ name: "binaries/yt-dlp", sidecar: true, args: true }` — validado por `tauri-build` al compilar (`cargo check` regenera `gen/schemas/capabilities.json` con el permiso resuelto, confirmando que el identificador y la forma del scope son válidos). Los binarios reales **no se commitean** (`src-tauri/binaries/.gitignore` ignora todo menos el propio `.gitignore`, ~15-20MB por plataforma); se traen con `scripts/fetch-yt-dlp.mjs` (`bun run fetch:yt-dlp`, o `--all` para las 5 target-triples soportadas), que pega contra la API de releases de GitHub y nombra el binario descargado como `yt-dlp-<target-triple>[.exe]` (convención de sidecar de Tauri). `yt-dlp_macos` es universal2 y cubre `x86_64-apple-darwin`/`aarch64-apple-darwin` con el mismo asset. Verificado en este entorno (Linux x86_64): binario descargado, ejecutable, `--version` responde `2026.07.04`. **Verificado en ventana Tauri real (Windows)** por el usuario: el sidecar se invoca correctamente vía `Command.sidecar('binaries/yt-dlp')`.
    - **19a-bis. Sidecars `ffmpeg` + `ffprobe` (transcodificación a MP3 real).** _Cerrado._ **Decisión surgida al implementar 19a:** `yt-dlp -x --audio-format mp3` no transcodea nada por sí solo — delega en `ffmpeg` como post-procesador externo (subproceso que **yt-dlp spawnea directo**, no algo que la capa JS invoque). Sin él, lo único bajable sin transcodear es el contenedor nativo que entrega YouTube (webm/opus o m4a/aac), rompiendo la promesa "MP3" del roadmap. Se decidió bundlear también `ffmpeg` en vez de degradar a guardar el audio nativo — y, ya en verificación real, se sumó un tercer sidecar `ffprobe` (el postprocesador de yt-dlp lo necesita además de `ffmpeg` para analizar el media; sin él falla con "ffprobe and ffmpeg not found" aunque `ffmpeg` sí esté presente). `tauri.conf.json`: `bundle.externalBin: ["binaries/yt-dlp", "binaries/ffmpeg", "binaries/ffprobe"]`. `scripts/fetch-ffmpeg.mjs` (mismo patrón que `fetch-yt-dlp.mjs`, `bun run fetch:ffmpeg` / `--all`) trae **ambos binarios** por plataforma: Linux (x86_64/aarch64) y Windows (x86_64) desde los builds estáticos GPL de `yt-dlp/FFmpeg-Builds` (`.tar.xz` vía `tar`, `.zip` vía `unzip` en Unix o `Expand-Archive` de PowerShell en Windows nativo — sin dependencia de `unzip.exe`, que no viene por defecto); macOS (x86_64) desde evermeet.cx (dos builds single-binary, uno por herramienta) — `aarch64-apple-darwin` reusa los binarios x86_64, corre bajo Rosetta 2 (limitación conocida y documentada, no hay build arm64 nativa gratuita mantenida). **No requiere capability nueva de `shell:allow-execute`**: ni `ffmpeg` ni `ffprobe` los invoca la capa JS/Tauri sino `yt-dlp` mismo como subproceso vía el flag `--ffmpeg-location` (que acepta un **path a archivo**, no a directorio — yt-dlp deriva la ubicación de `ffprobe` del mismo directorio), así que sólo necesitan estar en disco (resuelto en 19b) — no pasa por el plugin shell. **Verificado en ventana Tauri real (Windows)** por el usuario: pipeline completo yt-dlp→ffmpeg→ffprobe→mp3 funcionando de punta a punta.
    - **19b. `YoutubeDownloadService` + UI en `/music`.** _Cerrado._ Servicio nuevo `features/music/services/youtube-download.service.ts`: `isAvailable()` (gate por `PlatformService.current === 'tauri'`, doble-chequeado también dentro de `download()` como defensa en profundidad, no sólo en la UI), `isValidUrl()` (regex `youtube.com/watch?v=`/`youtu.be/`) y `download(url)` que orquesta dos corridas del sidecar `yt-dlp` (`Command.sidecar('binaries/yt-dlp', …).execute()`, mismo mecanismo de 19a) — una rápida `--skip-download --print "%(title)s"` sólo para el título (evita parsear stdout mezclado con logs de progreso de la descarga real) y otra real `-x --audio-format mp3 --audio-quality 0 --ffmpeg-location <path> -o <tempDir>/<uuid>.%(ext)s` que escribe a un archivo temporal predecible (nombrado en JS con `crypto.randomUUID()` antes de invocar, así no hace falta parsear el nombre final de yt-dlp). Ambas corridas pasan `--extractor-args youtube:player_client=android` — YouTube exige un desafío de cifrado de firma que requiere un runtime JS (deno) para el cliente `web` por defecto; el cliente `android` no usa URLs cifradas y evita necesitar un cuarto sidecar sólo para ese desafío (verificado contra un video real). El archivo se lee con `readFile` de `@tauri-apps/plugin-fs`, se arma un `File` (`audio/mpeg`, nombre saneado del título) y se borra el temporal. **Resolución de la ruta de `ffmpeg`:** nuevo comando Rust `sidecar_path(name)` en `lib.rs` — Tauri copia todo `externalBin` junto al ejecutable principal tanto en dev como en producción, pero bajo el **nombre pelado** (`ffmpeg[.exe]`, sin sufijo de target-triple), no como `"<name>-<target-triple>"`; el comando primero busca ese nombre pelado (con y sin `.exe`) y sólo si no aparece cae al fallback por prefijo `"<name>-"` (útil si algún día se resuelve distinto). No requiere capability nueva (los comandos de la app, a diferencia de los de plugins, no pasan por el sistema de ACL). Errores nuevos `MCB-MUS-002` (plataforma no soportada), `MCB-MUS-003` (URL inválida), `MCB-MUS-004` (yt-dlp/ffmpeg/ffprobe fallaron o el archivo esperado no apareció). **UI:** input + botón "Descargar" en el header de `/music` (`AlbumLibraryContainer`, junto al botón "Subir MP3" existente, layout `flex-nowrap` con el input shrinkeable para que ambos controles convivan sin desbordar), deshabilitado con tooltip (`music.youtube.unavailableTooltip`) cuando `!youtubeAvailable`; al completar, `MusicLibraryService.addTracks([file])` reusa el pipeline existente (ID3, cover, write atómico) sin código nuevo — la pista aparece sola en la lista reactiva, sin necesidad de un toast de éxito separado. Verificado: `bun run typecheck`/`lint` limpios, 444/448 specs verdes (baseline preexistente de `main`, sin relación). **Verificado en ventana Tauri real (Windows)** por el usuario: descarga real de punta a punta (fetch de título, extracción, transcodificación a mp3, alta en biblioteca) y confirmado que en Capacitor/navegador el control queda deshabilitado con tooltip sin ruta posible hacia `download()`. **Addendum 2026-07-18 — Capacitor deja de estar deshabilitado.** `isAvailable()` pasa a `current === 'tauri' || current === 'capacitor'`. Nuevo plugin Capacitor propio `android/app/src/main/java/dev/frnco/micerebro/YoutubeDlPlugin.java` (`@CapacitorPlugin(name = "YoutubeDl")`, registrado a mano en `MainActivity.onCreate` vía `registerPlugin()`), respaldado por `youtubedl-android` (`io.github.junkfood02.youtubedl-android:library`+`:ffmpeg`, Maven Central, fork mantenido de yausername/youtubedl-android — bundlea yt-dlp sobre un runtime Python propio + ffmpeg nativo por ABI, sin depender de un sidecar externo porque Android no permite spawnear binarios arbitrarios fuera del sandbox de la app). `YoutubeDL.getInstance().init()`/`FFmpeg.getInstance().init()` corren una vez en `Plugin.load()`; `fetchTitle`/`download` son símiles 1:1 de los dos comandos yt-dlp de Tauri (mismo `--extractor-args youtube:player_client=android`, mismo flujo `-x --audio-format mp3 --audio-quality 0`), pero escriben al cache dir privado de la app (`getContext().getCacheDir()`) en vez de un tempDir de SO, y devuelven el mp3 como `base64` en la respuesta del plugin en vez de una ruta — el WebView no tiene acceso directo a rutas `file://` arbitrarias del sandbox nativo, así que el bridge de Capacitor serializa los bytes directo (`YoutubeDownloadService.downloadCapacitor()` decodifica con `atob` + `Uint8Array`). Bridge JS en `features/music/services/youtube-download-native.plugin.ts` (`registerPlugin<YoutubeDlNativePlugin>('YoutubeDl')`). Gradle: `android/app/build.gradle` suma las dos dependencias + `ndk.abiFilters` (`x86`, `x86_64`, `armeabi-v7a`, `arm64-v8a` — las libs nativas de la librería sólo existen para esas ABIs) y `AndroidManifest.xml` suma `android:extractNativeLibs="true"` (requisito documentado de la librería). Actualiza `MCB-MUS-002` (ya no aplica a Capacitor, sólo browser) y `MCB-MUS-004` (causas nuevas del lado nativo) en `docs/errors.md`. **Pendiente de verificación manual:** igual que el resto de §18, este sandbox no tiene Android SDK — la corrida real en dispositivo/emulador (init de la librería, descarga end-to-end, tamaño final del APK con las libs nativas embebidas) queda a cargo del usuario.
20. **Rutas de detalle legibles + resolución robusta de IDs en reload.** _Cerrado, verificado en navegador real 2026-07-08_ (reload duro en las 8 rutas de detalle + `/books/<slug>/<slug-capítulo>`, formato `<slug>-<uuid>` en las 8 entidades incluyendo fallback de título vacío, slug desactualizado post-rename sigue resolviendo por el UUID embebido, bare UUID viejo sigue andando, click-through sin regresiones, command palette y calendario navegando al formato nuevo, consola limpia en todo el recorrido; el único punto no disparado en vivo fue el link recordatorio→goal del toast, verificado sólo por inspección de código ya que el toast no llegó a dispararse en la sesión de prueba — mismo helper `entitySlugSegment` que el resto de los casos que sí pasaron, riesgo bajo). Bug real detectado 2026-07-07: recargar una URL de detalle anidada (ej. `/books/<id>/<chapterId>`) tira `MCB-FS-003` ("carpeta raíz movida o eliminada") aunque la carpeta exista y el workspace esté intacto — reproducido en `mibro.netlify.app`, mismo stack que reporta el usuario (`requireLoc` → `bookDir` → `readBook` → `loadBook`). Navegar a la misma URL en-app (sin reload) funciona sin problema. Causa raíz: cada `*Service` mantiene un mapa en memoria `idToLoc`/`idToPath` (UUID → carpeta/slug real en disco) que sólo se puebla cuando corre `refresh()`; hoy `refresh()` lo dispara `WorkspaceSidebarContainer` al construirse (`layout/containers/workspace-sidebar.container.ts`), no un resolver de ruta. En navegación in-app el sidebar ya refrescó antes de que exista el link; en un reload directo el componente de la ruta de detalle puede montarse y leer antes de que el sidebar exista, con el mapa vacío. `NotesService`/`TasksService`/`GoalsService`/`ListsService`/`WritingsService` ya toleran esto con un `findPath(id)` que re-camina el filesystem si el caché falla; `BooksService`/`GalleriesService` (images)/`FilesService` no tienen ese fallback — sólo `requireLoc()`, que explota directo. Además contradice §8: el mapa `id → ruta actual` debería vivir "en el índice" (persistido), no sólo en memoria por servicio y por pestaña. Cambio adicional de fondo: las URLs de detalle usan hoy el UUID crudo de la entidad (`/books/9563a49c-…`) en vez de un slug legible, en las 8 entidades con ruta de detalle (notes/tasks/goals/lists/writings/books/images/files) — sólo `books` encadena dos UUIDs (`/books/:id/:chapterId`), el resto usa un solo `:id`. **Partido en sub-pasos independientes**, cada uno cierra por sí solo:
    - **20a. Fallback `findPath()` en `BooksService`/`GalleriesService`/`FilesService`.** Paridad con el patrón ya probado de Writings/Notes: si `idToLoc`/`idToPath` no tiene el id, re-caminar el filesystem (`walkEntities`) buscando el `id` interno antes de tirar error, y sembrar el caché al encontrarlo. Elimina el crash de reload sin tocar rutas ni UI. Quita también los dos usos indebidos de `MCB-FS-003` para "id no encontrado en caché" (`books.service.ts`, `bookDir`/`requireLoc`) — ese código queda reservado sólo para cuando la carpeta raíz del workspace realmente no está (su definición real en `docs/errors.md`). Código nuevo `MCB-FS-008` ("entidad no encontrada tras refrescar el índice") para el caso "el id no existe ni tras el re-walk" (borrado real, no condición de carrera). _Cerrado._ Al ser directorio-por-entidad (no archivo-plano-con-sufijo como Writings/Notes), `BooksService`/`GalleriesService`/`FilesService` no reusan `walkEntities` literal — cada uno suma un `findLoc(id)` + `walkForLoc()` privados que recorren el árbol de carpetas buscando el meta file (`_book.json`/`_gallery.json`/`_collection.json`) cuyo `id` interno matchea, sembrando `idToLoc` en cada acierto (propio y ajeno) antes de devolver. `requireLoc` (sync, tiraba `FS_003` directo si el id no estaba en caché) se elimina y sus tres call sites (`bookDir`/`galleryDir`/`collectionDir`, `deleteXToTrash`, `moveXToFolder`) pasan a `await findLoc(id)`. El único throw de "id no encontrado" que sobrevive tras el walk (dentro de `bookDir`/`galleryDir`/`collectionDir`, cuando `getDir(parent, slug)` devuelve null pese a que `findLoc` lo ubicó) ahora es `MCB-FS-008`; el resto de los `FS_003` en esos archivos (carpeta raíz vía `requireRoot`, carpeta padre/`shelf` desaparecida en `moveXToFolder`) queda intacto por ser genuinamente sobre directorios, no sobre resolución de id. Verificado: `bun run typecheck` limpio, 444/448 specs verdes (mismo baseline preexistente que ya reportaba 19b, sin relación).
    - **20b. Resolver de ruta compartido que garantiza el índice poblado antes de leer.** En vez de depender de que `WorkspaceSidebarContainer` se construya primero, un resolver/guard de Angular Router (`core/fs/entity-ready.guard.ts` o similar) que awaitea `refresh()` del servicio del kind correspondiente antes de activar cualquier ruta de detalle (`/books/:id`, `/notes/:id`, etc.), en boot o en navegación directa. Con 20a ya no rompe, pero sin esto sigue habiendo una carrera latente y un flash de "no encontrado" evitable en toda entidad, no sólo books. _Cerrado._ `entityReadyResolver` (`core/fs/entity-ready.guard.ts`, `ResolveFn<boolean>`) espera primero a que `WorkspaceService.state` se asiente en uno de sus estados terminales (`ready`/`unsupported`/`needs-root`/`needs-permission`/`foreign-folder` — vía `toObservable` + `firstValueFrom`/`filter`, evitando pisar `checking`/`initializing`); si no quedó `ready`, deja pasar la ruta sin tocar nada (mismo comportamiento previo a este resolver para esos casos, la UI de onboarding ya vive fuera del router). Si está `ready`, awaitea `WorkspaceRefreshService.ensureReady()` — método nuevo que dedupea contra la propia llamada de boot de `WorkspaceSidebarContainer` (que ahora también llama `ensureReady()` en vez de `refreshAll()` directo): primer llamador dispara el walk real y cachea la promesa en vuelo, cualquier segundo llamador concurrente (el resolver disparado por un reload directo a una ruta de detalle, corriendo en paralelo al constructor del sidebar) espera la misma promesa en vez de re-caminar el filesystem dos veces; una vez resuelto exitosamente marca `ready = true` y no vuelve a re-caminar en navegaciones subsiguientes de la misma sesión. `refreshAll()` (usado sin dedupe por `SwitchVariantService` tras un checkout y por el botón de resync manual en `/settings`, que sí necesitan un re-walk real) sigue existiendo tal cual y ahora también marca `ready = true` al completar, así el siguiente `ensureReady()` no repite el trabajo que ya hizo. Errores durante el refresh dentro del resolver se tragan silenciosamente — las lecturas propias del container (`readBook`/`readNote`/etc., ya con el fallback de `findLoc`/§20a) siguen siendo las que muestran el error real, sin cambiar ese comportamiento preexistente. Cableado en las 8 rutas de detalle (`notes.routes.ts`, `tasks.routes.ts`, `goals.routes.ts`, `lists.routes.ts`, `writings.routes.ts`, `images.routes.ts`, `files.routes.ts`, y las dos de `books.routes.ts` — `:id` y `:id/:chapterId`) vía `resolve: { ready: entityReadyResolver }`. Verificado: `bun run typecheck` y `bun run lint` limpios, 444/448 specs verdes (mismo baseline preexistente).
    - **20c. Slugs legibles en la URL.** Helper único en `core/` (ej. `core/routing/entity-slug.ts`) que compone la URL de detalle como `<slug-del-título>-<id-corto>` en vez del UUID crudo, con el mismo criterio de normalización que ya usa `toSlug()` para nombres de archivo (§8). El componente de detalle sigue resolviendo por el `id` completo (embebido en el segmento) — el slug es cosmético/mnemónico, no reemplaza al UUID como fuente de verdad, así que renombrar el título no rompe links guardados. Aplica a las 8 entidades con ruta de detalle; `/books/:id/:chapterId` pasa a `/books/<slug-libro>/<slug-capítulo>`. _Cerrado._ `core/routing/entity-slug.ts`: `entitySlugSegment(title, id, fallback?)` arma `<toSlug(title)>-<id>` (id completo, no truncado — pese al nombre "id-corto" del roadmap, el propio texto exige que el componente resuelva por el id completo, así que el UUID va entero); `extractEntityId(segment)` matchea un UUID v4-shape al final del string vía regex y devuelve ese grupo, o el string completo tal cual si no matchea nada — lo que además da compat automática con links viejos pre-§20c (bookmarks que eran el UUID crudo sin slug: el regex matchea el string entero como "el UUID al final"). Los 9 containers de detalle (`notes`/`tasks`/`goals`/`lists`/`writings`/`images`/`files`.container.ts + `book-open`/`book-reader`.container.ts) extraen el id real con `extractEntityId()` antes de pasarlo a los servicios; `book-reader.container.ts` lo hace para `id` y `chapterId` por separado. Los ~28 call sites que arman `router.navigate([...])` hacia una ruta de detalle (wall/shelf/garden/index containers, atajos de creación en `WorkspaceSidebarContainer`, `kind-routes.ts#routeFor` usado por el command palette, `calendar-event.types.ts#eventRoute`, el link cruzado goal↔reminder en `reminder-toast.container.ts`) pasan a construir el segmento con `entitySlugSegment(title, id)`, usando el mismo fallback por kind que ya usan los servicios (`'libro'`/`'galeria'`/`'coleccion'`/`'capitulo'`, default `'nota'` para el resto, igual que `toSlug()` ya hacía puertas adentro). Varios `(open)="onOpen($event)"` en templates pasaron a `(open)="onOpen(x.id, x.title)"` porque el título no viajaba en el evento. `kind-routes.ts#parseDetailUrl` (consumido por `PaletteRecentsService` para trackear visitas recientes) usa `extractEntityId()` sobre el segundo segmento en vez de asumirlo id crudo — sin este fix hubiera guardado el slug completo como id. Verificado: `bun run typecheck` y `bun run lint` limpios, 444/448 specs verdes (mismo baseline preexistente).
    - **20d. Actualizar `docs/errors.md` y este documento.** Documentar `MCB-FS-008`, corregir el catálogo si algún otro servicio comparte el mismo antipatrón de `MCB-FS-003` mal usado, y anotar en §8 que el mapa `id → ruta` sigue siendo in-memory por servicio (no persistido en el índice) salvo que 20b/20a lo ameriten — evitar que la doc siga prometiendo algo que el código no cumple. _Cerrado._ `docs/errors.md`: la entrada de `MCB-FS-003` suma una nota de alcance aclarando que está reservado para la carpeta raíz del workspace, y deja registrada la deuda conocida — `findPath()` de `NotesService`/`TasksService`/`GoalsService`/`ListsService`/`WritingsService` y `BooksService#findChapterFile` todavía tiran `MCB-FS-003` para "id no encontrado tras el walk" (mismo antipatrón que 20a corrigió sólo en `bookDir`/`requireLoc` de las 3 entidades directorio-por-entidad) — registrada también como ítem sin fase asignada en `docs/deferred/index.md`. §8 (`docs/proyecto/filesystem.md`) corregido: la convención "IDs estables internos" ya no afirma que el mapa `id → ruta` vive persistido en el índice — aclara que es in-memory por servicio, reconstruido en cada `refresh()`, con el fallback de re-walk (20a) y el resolver de boot (20b) como las dos piezas que lo hacen confiable sin persistirlo.
21. **Responsive mobile.** Disparado por un reporte del usuario 2026-07-10: entrar desde el navegador de un celular Android no permite ninguna acción de escritura en el FS (diagnóstico aparte, ver §9/§18 — Chrome Android no implementa `showDirectoryPicker`, la vía mobile real es el empaquetado Capacitor de §18c) y, en la misma sesión, auditoría visual a 393×852px reveló que el shell nunca tuvo tratamiento responsive: `workspace-sidebar.container.css` (el rail de íconos, ver §4.6.14) no tenía ni un `@media`, así que en cualquier viewport angosto el rail se comía ~56px fijos del ancho y el contenido de cada feature desbordaba sin wrap. Como Capacitor renderiza el mismo WebView con el mismo CSS que el navegador (§18), este paso vale para ambos targets a la vez — no hace falta un tratamiento aparte por plataforma. **Sin convención de breakpoint centralizada** (§4.6.14): cada componente sigue hardcodeando su propio `@media (max-width: …)`; este paso introduce `480px` como el valor de facto para "viewport de celular" allí donde no existía ya un breakpoint más laxo pensado para ventana angosta de escritorio (600-1280px, ya cubiertos por pasos previos). **Alcance de esta entrada:** deja fundada la base (shell + 2 páginas) y releva el resto pendiente; no pretende cerrar todas las pantallas en una sola pasada. Subdividido en sub-pasos independientes:
    - **21a. Rail global: toggle + grilla overlay en mobile.** _Cerrado._ Afecta a todas las pantallas por igual porque el rail vive en el shell, no por feature.
